# 2026-05-07 日志 — @_all 测试战役 & 极客系彻底修复

## 背景

领航员发起多轮 @_all 测试（23:16→23:50→00:06），目标：确保全部 7-8 个 Bot 在飞书群聊中响应 @_all 全员通知。

## 发现 & 修复的问题

### 1. 极客系 Claude Bridge 8分钟死亡循环 ⚡ ROOT CAUSE FOUND

**症状：** 双桥接进程（geek + keke）每 7-10 分钟自动消亡，Keepalive 每 3 分钟复活，形成反复死亡-复活循环。

**根因链路：**
```
getWorstReadyState() 初始化 worst=3（CLOSED）
  → 循环检查 state > 3（永假）
    → 永远返回 3（CLOSED）
      → 外部看门狗每 2min 输出 "WebSocket still down"
        → Keepalive 读到后标记 WS 断线 >300s
          → Kill 进程 → 重启 → 循环
```

**修复（v4, src/feishu-bots.ts）：**
```typescript
// Before:
let worst = 3; // CLOSED — 初始值已经是最高，state > 3 永假
if (state != null && state > worst) worst = state;

// After:
if (this.bots.size === 0) return 3; // CLOSED only if no bots
let worst = 0; // 从最佳状态开始，找实际最差
if (state != null && state > worst) worst = state;
```

**验证：** v4 部署后 Keepalive 日志无 "WebSocket still down" 记录。外部看门狗正确返回 state=1（OPEN）。

### 2. 极客系 @_all 不响应

**症状：** @_all 消息进入桥接后，日志显示 `hasAllKeyword: true` 但 `feishuEnableAllKeyword:` 为空字符串 → `allKeywordBypass = true && ""` = falsy → 消息被忽略。

**根因：** config.env 文件明确有 `CTI_FEISHU_ENABLE_ALL_KEYWORD=true`（34字节，ASCII验证），但 `parseEnvFile()` 解析后值为空字符串。原因未查明（可能为 env file 读取时序问题或换行符处理bug）。

**修复（v5, src/feishu.ts）：**
```typescript
// Before: 依赖配置开关
allKeywordBypass = hasAllKeyword && this.config.feishuEnableAllKeyword;

// After: @_all 无条件放行
allKeywordBypass = hasAllKeyword || this.config.feishuEnableAllKeyword;
```

**验证（00:06 测试）：** 双桥接同时响应 @_all：
- 极客Claude: `"极客系在线，0006 收到。⚡"` （16:06:23）
- 科科Claude: 详细分析日志确认 mentions 为空时关键词绕过成功

### 3. getWsReadyState() 回退Bug（v2修复，已部署）

`feishu.ts` 中当底层 WS 实例被 GC 回收后，回退逻辑返回 1（OPEN）而非 3（CLOSED），导致内部看门狗无法检测到 WS 断线。

```typescript
// Bug (Before):
if (this.wsHasEverConnected && this.wsClient) return 1; // OPEN

// Fix (v2):
if (this.wsHasEverConnected && this.wsClient) return 3; // CLOSED
```

### 4. 法务官 (Hermes Legal) 启动问题

**症状：** 电脑重启后法务官未自动启动（default/touyan 正常自启）。

**根因：** PID 6194 以 ROOT 用户运行，使用 `/root/.hermes/` 空配置目录（无 Feishu 凭证），日志显示 "No messaging platforms enabled"。

**修复：**
- Kill root PID 6194
- 清理 `/root/.hermes/profiles/legal/gateway.lock`
- 以 joe 用户重启：`sudo -u joe hermes -p legal gateway run`
- 法务官 23:31 上线，Feishu WS 连接成功

**待优化：** 法务官 profile 需加入 tmux 自启队列（当前只有 default + touyan）。

### 5. 科科 Routing 误触发

**症状：** 科科对非 @ 自己的群消息也响应。

**根因：** 路由配置使用 `@_user_` 关键词，桥接将飞书 `<at>` 标签转换为 `@_user_<id>` 格式，任何 @mention 都触发科科。

**修复：** 将 `@_user_` 替换为具体的 botOpenId：
- `config.env`（geek bridge）: `ou_a4a4990e2b9c56d73fb52f904bb71a48`
- `config.keke.env`（keke bridge）: `ou_b08f87f7c7934a44a1afefb5e0090079`

## 技术洞察

### WSClient.reConnect() 在 Windows 上静默失败
SDK 的 `WSClient.reConnect(false)` 在 Windows 上从不触发（日志中从未出现 "[feishu] WSClient reconnecting..."）。`process.exit(1)` + Keepalive 重启是唯一可靠的恢复机制。

### 飞书 @_all 事件特性
- mentions 数组为空（不含任何 bot 的 open_id）
- 原始内容为 `{"text":"@_all 测试内容"}`
- 必须通过关键词绕过才能检测到 @_all
- Hermes 通过 `_mentions_self()` 检查 `"@_all" in raw_content` 实现

### Hermes "所有人" 关键词过敏感问题（待修复）
对话中的 "所有人" 也会触发 Hermes 响应（如 "艾特所有人的消息"），需优化为仅匹配 `@_all` 和 `@所有人` 格式。
